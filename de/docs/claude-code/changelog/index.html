Integrationen

Changelogs

Schreiben Sie mit /mergecat:changelog ein Changelog nach Keep a Changelog: für die noch nicht veröffentlichten Änderungen, eine Version, alle Releases oder einen beliebigen Bereich aus Tags, Datumsangaben und Commits.

Auf GitHub bearbeiten

Mithilfe von KI aus dem Englischen übersetzt. Im Zweifel gilt die englische Fassung.

/mergecat:changelog macht aus dem, was in den Main-Branch kam, ein Changelog im Format Keep a Changelog. Jeder gemergte Pull Request, jeder Merge und jeder direkte Commit ist ein Changeset, bereits in Abschnitte einsortiert (Added, Changed, Deprecated, Removed, Fixed, Security); Claude schreibt den Entwurf für die Menschen um, die Ihr Projekt nutzen. Das Ergebnis ist ein Dokument der Unterhaltung, auf Englisch und in Markdown, sofern Sie nichts anderes wünschen.

Zuerst die Compliance-Frage

In einer neuen Claude-Code-Sitzung beginnt das erste Changelog mit der Compliance-Frage (Claude-Team- oder -Enterprise-Konto; falls nicht, Kenntnis der EU-KI-Verordnung (EU AI Act) und der NIS-2-Richtlinie (NIS2)). Die Antwort wird auf Ihrem Computer protokolliert. Siehe KI-Nutzungsnachweise.

Verwendung

/mergecat:changelog [from..to | version | all] [pdf] [lang:<code>] [update file]

Sie können auch in eigenen Worten fragen, zum Beispiel „Changelog von v1.2.0 bis heute“ oder „Release Notes von v1.3.0 auf Deutsch als PDF“.

Argumente

ArgumentChangelog
(keines)Was seit dem neuesten Release neu ist, als ## [Unreleased]
from..toNur dieser Bereich; siehe Bereiche
1.4.0 (eine Version)Die noch nicht veröffentlichten Änderungen als ## [1.4.0] - <today>
allAlle Releases aus den Versions-Tags (bis zu 20), mit dem Kopfteil von Keep a Changelog
pdfEin PDF-Dokument statt Markdown; auch „als PDF“, „in PDF“, format:pdf
md, markdownMarkdown, der Standard
lang:<code>Die Sprache des Changelogs, z. B. lang:it; auch in Worten, „auf Italienisch“
update fileZusätzlich die CHANGELOG.md des Projekts aktualisieren; ebenso, wenn Sie in Worten darum bitten, CHANGELOG.md zu aktualisieren oder zu schreiben

Alle anderen Wörter sind Anweisungen für den Text, zum Beispiel zur Zielgruppe oder zum Detailgrad („für Endbenutzer“, „interne Änderungen einbeziehen“).

Bereiche

Jedes Ende eines Bereichs ist ein Tag, ein Datum oder ein Commit, in beliebiger Kombination. Eckige Klammern sind erlaubt ([v1.2.0..v1.3.0]), und ein Ende kann offen bleiben.

BereichÄnderungen
v1.2.0..v1.3.0Das Release v1.3.0
v1.2.0..2026-03-31Nach v1.2.0 bis zum Ende des 31. März 2026
2026-01-01..v1.3.0Ab dem 1. Januar 2026 (einschließlich) bis v1.3.0
2026-01-01..2026-03-31Was im ersten Quartal in den Branch kam
v1.2.0..abc1234, 2026-01-01..abc1234Bis zu diesem Commit
abc1234..v1.3.0, abc1234..2026-03-31, abc1234..def5678Nach diesem Commit
v1.3.0..Bis zur neuesten Änderung
..v1.0.0Ab dem ersten Commit
  • Der Anfang ist ausgeschlossen, das Ende ist eingeschlossen.
  • Ein Datum bezieht sich darauf, wann eine Änderung in den Main-Branch kam (First-Parent-Verlauf), in der lokalen Zeitzone Ihres Computers. Als Anfang bedeutet es „ab diesem Tag“, als Ende „bis zum Ende dieses Tages“.
  • Datumsangaben haben das Format YYYY-MM-DD, optional mit Uhrzeit und Zeitzone (2026-03-31T18:00, 2026-03-31 18:00+02:00).
  • Ein Commit ist ein SHA oder ein Branch-Name.
  • Ist ein Name zugleich ein Tag und ein Datum, hat das Tag Vorrang. Vertauschte Enden werden gemeldet, und Claude teilt Ihnen mit, wie jedes Ende aufgelöst wurde.
  • Ein unbekanntes Ende oder ein ungültiges Datum wird in einer Zeile erklärt, mit gültigen Enden aus den Tags als Vorschlag; Claude rät nicht.

Führen Sie /mergecat:tags aus, um die Tags und sofort verwendbare Bereiche zu sehen.

Sprache

  • Das Changelog ist auf Englisch, sofern Sie nicht mit lang:<code> oder in Worten eine andere Sprache anfordern. Wenn Sie Ihre Anfrage in einer anderen Sprache schreiben, fordern Sie damit nicht diese Sprache an.
  • Titel, Einleitung, Abschnittsüberschriften und „Unreleased“ werden für Englisch, Italienisch, Deutsch, Französisch und Spanisch (en, it, de, fr, es) fertig übersetzt geliefert. Für andere Sprachen übersetzt Claude sie.
  • Claude schreibt jede Änderungszeile in der angeforderten Sprache. Versionen, Datumsangaben, Pull-Request-Links, Issue-Verweise, Code-Bezeichner und Dateinamen bleiben unverändert.
  • Wenn Sie eine CHANGELOG.md aktualisieren lassen, die in einer anderen Sprache geschrieben ist als der angeforderten (oder als Englisch, wenn Sie keine angefordert haben), fragt Claude einmal nach, welche Sprache verwendet werden soll.

Format

Markdown ist der Standard. Fordern Sie bei Bedarf PDF an (pdf, „als PDF“): Claude erstellt das endgültige Markdown, konvertiert es mit dem Tool render_pdf und übergibt Ihnen die Datei mit dem Namen changelog-<repository>-<version or range>.pdf. Das PDF wird außerhalb Ihres Projekts geschrieben (im Scratchpad von Claude oder im temporären Ordner des Systems).

PDFs haben das Format A4 und verwenden die Standard-PDF-Schriften (Helvetica, Courier):

  • Latin-1-Text, der die westeuropäischen Sprachen abdeckt, wird unverändert gedruckt;
  • einige typografische Zeichen werden zu ASCII: → wird zu ->, typografische Anführungszeichen werden zu geraden, … wird zu ..., € wird zu EUR;
  • Zeichen anderer Schriftsysteme (Griechisch, Kyrillisch, Chinesisch, Japanisch, …) und Emoji werden durch ? ersetzt. Verwenden Sie Markdown für Sprachen, die in anderen Schriftsystemen geschrieben werden.

Das PDF unterstützt Überschriften, Absätze, Listen, Zitate, horizontale Linien, Code, einfache Tabellen, Fett- und Kursivschrift sowie Links. CHANGELOG.md im Projekt ist immer Markdown.

Wohin das Changelog kommt

Das Changelog ist ein Dokument der Unterhaltung. Claude veröffentlicht es als Markdown-Artefakt, sendet es als Datei, die Sie öffnen und herunterladen können (changelog-<repository>-<version or range>.md), oder zeigt es als Markdown-Block in der Antwort. In Ihr Repository wird nichts geschrieben.

Nur mit update file oder wenn Sie in Worten darum bitten, aktualisiert Claude zusätzlich CHANGELOG.md im Stammverzeichnis des Repositorys:

  • jeder vorhandene Release-Abschnitt bleibt genau so, wie er ist;
  • die Änderungen kommen in ## [Unreleased] oder unter eine neue, darunter eingefügte Versionsüberschrift, gefolgt von einem leeren ## [Unreleased];
  • die Linkreferenzen am Ende werden aktualisiert;
  • existiert die Datei nicht, erstellt Claude sie mit dem Kopfteil von Keep a Changelog;
  • ein Bereich, der kein Release ist (er endet bei einem Datum oder einem Commit), kommt nicht in CHANGELOG.md: Claude weist darauf hin und liefert nur das Dokument.

Claude liest eine vorhandene CHANGELOG.md immer zuerst (nur lesend). Ist ihre neueste Version älter als das neueste Versions-Tag, enthält das Changelog auch die Releases, die in der Datei fehlen.

Wie Claude den Entwurf bearbeitet

Die mergecat-Tools liefern einen Entwurf und strukturierte Daten zu jedem Changeset: Abschnitt und Grund für dessen Wahl, Nummer und Link des Pull Requests, Branch, Commits sowie die Kennzeichen „Breaking“ und „intern“. Claude geht dann so vor:

  • schreibt eine Zeile pro für Benutzer sichtbarer Änderung, für die Benutzer formuliert, und behält Pull-Request-Links und Issue-Verweise bei;
  • beschreibt vage Einträge („Merge branch …“) anhand ihrer Commits;
  • behält BREAKING-Markierungen bei und stellt Breaking Changes in ihrem Abschnitt an den Anfang;
  • lässt interne Einträge (Doku, Tests, CI, Chores) weg, es sei denn, sie sind für Benutzer relevant oder Sie haben um alles gebeten;
  • korrigiert einen Abschnitt, wenn der Grund in den Daten eindeutig falsch ist, und führt Duplikate zusammen;
  • fügt nie eine Änderung hinzu, die nicht in der Ausgabe des Tools steht.

Zum Schluss fasst Claude zusammen: das Release oder den Bereich und wie jedes Ende aufgelöst wurde, die Sprache und das Format, die Anzahl der Änderungen pro Abschnitt und alles, was Ihre Entscheidung erfordert: einen unklaren Abschnitt, eine Änderung ohne Pull Request, einen Breaking Change, vertauschte Enden. Prüfen Sie das Changelog, bevor Sie es veröffentlichen.

Pull-Request-Daten

Ohne Token stützt sich das Changelog auf Git-Daten: Merge-Nachrichten, Branch-Namen und Commit-Betreffs, und Claude weist in einer Zeile darauf hin, dass Titel von Pull Requests GITHUB_TOKEN erfordern. Starten Sie Claude Code für Repositorys auf github.com mit GITHUB_TOKEN (oder GH_TOKEN), gesetzt auf ein Token, das die Pull Requests des Repositorys lesen kann: Zeilen und Abschnitte ergeben sich dann aus Titeln, Labels und verknüpften Issues der Pull Requests. Siehe Pull-Request-Daten.

Hat der Verlauf keine Merge-Commits oder verwendet er Squash-Merges, weist Claude darauf hin, dass sich die Gruppierung auf Commit-Nachrichten stützt; siehe Grenzen und Integrationsarten.
