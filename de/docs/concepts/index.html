Erste Schritte

So funktioniert mergecat

Wie mergecat den Git-Verlauf eines Branches in Changesets umwandelt, die gemergten Branches benennt und mit Squash, Rebase und anderen Integrationsarten umgeht.

Auf GitHub bearbeiten

Mithilfe von KI aus dem Englischen übersetzt. Im Zweifel gilt die englische Fassung.

mergecat erfindet keine Struktur: Alles, was es zeigt, stammt aus dem Commit-Graphen, den Commit-Nachrichten und, wenn verbunden, aus den Pull Requests des Hosting-Dienstes. Diese Seite erklärt die Regeln, damit Sie vorhersagen können, was Sie sehen werden, und erkennen, wenn ein Verlauf ihnen nicht folgt.

Der First-Parent-Durchlauf

Wenn Sie ein Feature in main mergen, speichert der Merge-Commit zwei Eltern-Commits: Der erste ist der Commit, auf dem main stand, der zweite die Spitze des Features. Wer von der Spitze eines Branches aus nur den ersten Eltern-Commits folgt, erhält seine Hauptlinie (Mainline): die Folge der Zustände, die der Branch selbst durchlaufen hat.

mergecat durchläuft diese First-Parent-Kette, die neuesten zuerst, und macht aus jedem Commit darauf einen Eintrag:

Commit auf der HauptlinieEintrag
Ein Eltern-CommitEin direkter Commit: auf dem Branch selbst erstellt, eine Zeile.
Zwei oder mehr Eltern-CommitsEine Integration (Changeset): ein Merge, als Gruppe mit den Commits dargestellt, die er gebracht hat.

Was eine Integration enthält

Für einen Merge M mit den Eltern-Commits P1, P2..Pn enthält die Gruppe die Commits, die von P2..Pn aus erreichbar sind, aber nicht von P1. In Git ausgedrückt:

git log P2..Pn ^P1

Das sind genau die Commits, die über M in den Branch kamen. In diesem Beispiel bringt der Merge von feature bei M die Commits C und D hinein:

main      A───B───────M
               \     /
feature         C───D

Vorwärtsintegration

Feature-Branches mergen oft main zurück, um aktuell zu bleiben („merge main into feature“). Die Commits, die auf diesem Weg aus main kamen, sind von P1 aus erreichbar und werden daher in der Gruppe des Features nicht noch einmal gezählt. Die „merge main into feature“-Commits selbst sind standardmäßig ausgeblendet: Sie haben nichts Neues in den Branch gebracht.

Schalten Sie Vorwärtsintegrations-Merges ausblenden unter Filter aus, um sie zu sehen. Sie erscheinen dann innerhalb der Gruppe mit einem Chip Vorwärtsintegration.

Verschachtelte Merges

Wenn Feature A in Feature B gemergt wird und B in main, wird A zu einer Untergruppe im Changeset von B, gekennzeichnet als Verschachtelter Merge. Klappen Sie sie auf, um die Commits von A zu sehen.

Octopus-Merges

Ein Merge von drei oder mehr Branches auf einmal erhält das Flag Octopus. Seine Gruppe hat eine Spur pro gemergtem Branch, jeweils mit dem Branch-Namen als Überschrift, und die Spalte Branch / PR verbindet die Namen mit +.

Leere Merges

Ein Merge, der keinen Commit gebracht hat, der nicht schon auf dem Branch war, erhält das Flag leer.

Den gemergten Branch benennen

Git speichert keine Branch-Namen in Commits. mergecat sucht den Namen in dieser Reihenfolge und hört bei der ersten Quelle auf, die ihn kennt:

  1. Die Merge-Nachricht. Funktioniert offline und übersteht das Löschen des Branches.
  2. Der Pull Request vom Hosting-Dienst (verbundener Modus). Funktioniert auch, nachdem der Branch gelöscht wurde.
  3. Ein Branch, der noch auf den gemergten Commit zeigt, lokal oder remote.
  4. Der kurze SHA des gemergten Commits, wenn nichts anderes bekannt ist.

Fahren Sie mit der Maus über einen Branch-Chip, um zu sehen, welche Quelle verwendet wurde; der Detailbereich zeigt sie unter Branch. Wenn der Name unbekannt ist und eine Verbindung ihn ermitteln würde, zeigt der Chip ein Schlosssymbol.

Diese Merge-Nachrichten werden erkannt:

Geschrieben vonNachrichtWas mergecat liest
git mergeMerge branch 'feature/x' into main, Merge branches 'a', 'b' and 'c'Branch-Namen
git pullMerge branch 'x' of https://…Branch-Name
git merge eines Remote-BranchesMerge remote-tracking branch 'origin/x'Branch-Name ohne das Remote
git merge eines TagsMerge tag 'v1.2.0'Tag-Name
GitHubMerge pull request #12 from org/feature-xPull-Request-Nummer und Branch
GitLabMerge branch 'x' into 'main' mit See merge request group/project!12 im NachrichtentextBranch, Merge-Request-Nummer und Titel
BitbucketMerged in feature-x (pull request #12)Branch und Pull-Request-Nummer
Azure DevOpsMerged PR 12: TitleNur Pull-Request-Nummer und Titel

Eine Konvention, die Namen lesbar hält

Schließen Sie Pull Requests mit einem Merge-Commit ab (kein Fast-Forward) und setzen Sie den Branch-Namen oder die Work-Item-ID in den Titel des Pull Requests. Der Titel landet in der Merge-Nachricht und übersteht das Löschen des Branches.

Integrationsarten

Wie Ihr Team Pull Requests abschließt, bestimmt, was der Verlauf enthält. mergecat zeigt jede Art so getreu, wie es der Graph zulässt, und sagt, wenn die Gruppierung unvollständig ist.

Wie Pull Requests abgeschlossen werdenWas mergecat zeigt
Merge-Commit (kein Fast-Forward), einschließlich semilinearem Merge von Azure DevOpsGruppen.
SquashEin Commit. Mit Squash gekennzeichnet, wenn die Nachricht wie ein Pull Request aussieht (Title (#12), Merged PR 12: Title, Merged in von Bitbucket). Verbunden: mit Squash-Merge-PR gekennzeichnet, und der Detailbereich listet die ursprünglichen Commits auf.
Rebase und Fast-ForwardDirekte Commits. Verbunden: pro Pull Request als Rebase-Merge-PR gruppiert.
Fast-Forward eines Features, das Vorwärtsintegration verwendet hat, oder git pull-Merges auf dem Branch selbstMit invertiert gekennzeichnet: Ab dort folgt der First-Parent-Pfad möglicherweise der falschen Seite („Foxtrot“-Merges).
Shallow CloneEine Warnung; Gruppen können unvollständig sein. Der Commit, an dem der Verlauf abgeschnitten ist, ist mit Shallow gekennzeichnet.

Wenn eine dieser Situationen den Branch betrifft, erscheint über der Liste eine Warnleiste:

WarnungWann
Dieser Branch hat keine Merge-CommitsJeder Eintrag ist ein direkter Commit, typischerweise bei Rebase- oder Fast-Forward-Merges. Verbinden Sie den Hosting-Dienst, um sie zu gruppieren.
Dieser Branch wird nicht mit No-Fast-Forward-Merges integriertKeine Merges, und Pull Requests sehen nach Squash-Merges aus.
Gemischte IntegrationsartenEinige Pull Requests sehen zwischen regulären Merges nach Squash-Merges aus.
N merge(s) merged "main" into something elseEin oder mehrere invertierte Merges.
Dies ist ein Shallow CloneFühren Sie git fetch --unshallow aus, um vollständige Ergebnisse zu erhalten.

Mehr zu jeder Grenze und wie Sie sie vermeiden: Grenzen und Integrationsarten.

Leistung

mergecat startet nicht einen Git-Prozess pro Merge. Es liest den gesamten Verlauf des Branches mit einem einzigen git log und berechnet die Gruppen dann im Speicher: Es durchläuft die First-Parent-Kette ab dem ältesten Commit und lässt jeden Merge die Commits beanspruchen, die noch nicht beansprucht wurden. Der Aufwand wächst linear mit der Anzahl der Commits; ein Verlauf mit 11.000 Commits ist in deutlich unter einer Sekunde indiziert. Die Kopfzeile der Liste zeigt, wie lange das letzte Lesen gedauert hat (read in … ms).

Alles andere geschieht bei Bedarf:

  • Diffs werden mit git diff berechnet, wenn Sie eine Zeile auswählen;
  • Pull-Request-Daten (verbunden) werden für die Einträge geladen, die Sie gerade ansehen, und pro Commit-SHA zwischengespeichert, sodass sie über Fetches hinweg gültig bleiben;
  • die zuletzt gelesenen Verläufe bleiben im Speicher, sodass der Wechsel zurück zu einem Branch, dessen Spitze sich nicht bewegt hat, sofort erfolgt.

Liste und Graph

Die Seite Verlauf zeigt denselben Verlauf in zwei Layouts:

  • Liste: die Changesets, mit Integrationen, die Sie bis zu den Commits aufklappen können, die sie gebracht haben.
  • Graph: jeder Commit mit seinen Spuren, wie git log --graph, einmal für den gesamten Verlauf berechnet. Jeder Commit trägt einen Chip mit dem Changeset, über das er in den Branch kam; der Chip ist auf dem Commit hervorgehoben, der das Changeset integriert hat.

Das Graph-Layout: jeder Commit, markiert mit seinem Changeset.

Bewusst nur lesend

mergecat führt Git-Befehle aus, die lesen. Es schreibt nur, wenn Sie selbst eine Aktion starten:

AktionWas ausgeführt wird
Abrufen auf der Seite Branchesgit fetch --all --tags --prune (Ihre lokalen Branches werden nicht verändert)
Neues Tag, Pushengit tag, git push <remote> refs/tags/<name>
Neuer Pull RequestEin Aufruf beim Hosting-Dienst

Abrufen und Tag-Pushes verwenden Ihre Git-Anmeldedaten (Ihren Credential Helper); mergecat fragt nie nach einem Git-Passwort.
