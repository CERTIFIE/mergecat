Integrations

Changelogs

Write a Keep a Changelog changelog with /mergecat:changelog, for the unreleased changes, a version, every release or any range of tags, dates and commits.

Edit on GitHub

/mergecat:changelog turns what entered the main branch into a changelog in the Keep a Changelog format. Each merged pull request, merge or direct commit is one changeset, already sorted into sections (Added, Changed, Deprecated, Removed, Fixed, Security); Claude rewrites the draft for the people who use your project. The result is a document of the conversation, in English and Markdown unless you ask otherwise.

Compliance question first

In a new Claude Code session, the first changelog starts with the compliance question (Claude Team or Enterprise account; if not, awareness of the EU AI Act and NIS2). The answer is recorded on your computer. See AI usage records.

Usage

/mergecat:changelog [from..to | version | all] [pdf] [lang:<code>] [update file]

You can also ask in your own words, for example “changelog from v1.2.0 to today” or “release notes of v1.3.0 in German as PDF”.

Arguments

ArgumentChangelog
(none)What is new since the newest release, as ## [Unreleased]
from..toOnly that range; see Ranges
1.4.0 (a version)The unreleased changes as ## [1.4.0] - <today>
allEvery release from the version tags (up to 20), with the Keep a Changelog header
pdfA PDF document instead of Markdown; also “as PDF”, “in PDF”, format:pdf
md, markdownMarkdown, the default
lang:<code>The language of the changelog, e.g. lang:it; also in words, “in Italian”
update fileAlso update the project’s CHANGELOG.md; also when you ask in words to update or write CHANGELOG.md

Any other words are instructions for the text, for example the audience or the level of detail (“for end users”, “include internal changes”).

Ranges

Each end of a range is a tag, a date or a commit, in any combination. Brackets are allowed ([v1.2.0..v1.3.0]) and an end can be left open.

RangeChanges
v1.2.0..v1.3.0The release v1.3.0
v1.2.0..2026-03-31After v1.2.0, up to the end of 31 March 2026
2026-01-01..v1.3.0From 1 January 2026 (included) up to v1.3.0
2026-01-01..2026-03-31What entered the branch in the first quarter
v1.2.0..abc1234, 2026-01-01..abc1234Up to that commit
abc1234..v1.3.0, abc1234..2026-03-31, abc1234..def5678After that commit
v1.3.0..Up to the latest change
..v1.0.0From the first commit
  • The start is excluded and the end is included.
  • A date refers to when a change entered the main branch (first-parent history), in the local time zone of your computer. As start it means “from that day on”, as end “up to the end of that day”.
  • Dates are YYYY-MM-DD, optionally with a time and a time zone (2026-03-31T18:00, 2026-03-31 18:00+02:00).
  • A commit is a SHA or a branch name.
  • If a name is both a tag and a date, the tag wins. Swapped ends are reported, and Claude tells you how each end was resolved.
  • An unknown end or an invalid date is explained in one line, with valid ends suggested from the tags; Claude does not guess.

Run /mergecat:tags to see the tags and ready-to-use ranges.

Language

  • The changelog is in English unless you ask for another language with lang:<code> or in words. Writing your request in another language is not a request for that language.
  • The title, the preamble, the section headings and “Unreleased” come translated for English, Italian, German, French and Spanish (en, it, de, fr, es). For other languages Claude translates them.
  • Claude writes every change line in the requested language. Versions, dates, pull request links, issue references, code identifiers and file names stay as they are.
  • When you ask to update a CHANGELOG.md written in a different language from the requested one (or from English, when you did not ask for one), Claude asks once which language to use.

Format

Markdown is the default. Ask for PDF (pdf, “as PDF”) when you need it: Claude builds the final Markdown, converts it with the render_pdf tool and gives you the file, named changelog-<repository>-<version or range>.pdf. The PDF is written outside your project (Claude’s scratchpad or the system temporary folder).

PDFs are A4 and use the standard PDF fonts (Helvetica, Courier):

  • Latin-1 text, which covers the Western European languages, is printed as is;
  • a few typographic characters become ASCII: → becomes ->, curly quotes become straight quotes, … becomes ..., € becomes EUR;
  • characters of other scripts (Greek, Cyrillic, Chinese, Japanese, …) and emoji are replaced with ?. Use Markdown for languages written in other scripts.

The PDF supports headings, paragraphs, lists, quotes, horizontal rules, code, simple tables, bold, italic and links. CHANGELOG.md in the project is always Markdown.

Where the changelog goes

The changelog is a document of the conversation. Claude publishes it as a Markdown artifact or sends it as a file you can open and download (changelog-<repository>-<version or range>.md), or shows it as a Markdown block in the reply. Nothing is written into your repository.

Only with update file, or when you ask in words, Claude also updates CHANGELOG.md at the root of the repository:

  • every existing release section stays exactly as it is;
  • the changes go into ## [Unreleased], or under a new version heading placed below it, followed by an empty ## [Unreleased];
  • the link references at the bottom are updated;
  • if the file does not exist, Claude creates it with the Keep a Changelog header;
  • a range that is not a release (it ends at a date or a commit) does not go into CHANGELOG.md: Claude says so and delivers only the document.

Claude always reads an existing CHANGELOG.md (read only) first. When its newest version is older than the newest version tag, the changelog also includes the releases missing from the file.

How Claude edits the draft

The mergecat tools return a draft and structured data for each changeset: section and the reason it was chosen, pull request number and link, branch, commits, and breaking and internal flags. Claude then:

  • writes one line per user-visible change, for users, keeping pull request links and issue references;
  • describes vague items (“Merge branch …”) from their commits;
  • keeps BREAKING markers and puts breaking changes first in their section;
  • leaves out internal items (docs, tests, CI, chores) unless they matter to users or you asked for everything;
  • fixes a section when the reason in the data is clearly wrong, and merges duplicates;
  • never adds a change that is not in the tool output.

At the end, Claude summarises the release or range and how each end was resolved, the language and format, the number of changes per section, and anything that needs your decision: an unclear section, a change without a pull request, a breaking change, swapped ends. Review the changelog before you publish it.

Pull request data

Without a token, the changelog relies on Git data: merge messages, branch names and commit subjects, and Claude says in one line that pull request titles need GITHUB_TOKEN. For github.com repositories, start Claude Code with GITHUB_TOKEN (or GH_TOKEN) set to a token that can read the repository’s pull requests: lines and sections then come from pull request titles, labels and linked issues. See Pull request data.

If the history has no merge commits or uses squash merges, Claude says that the grouping relies on commit messages; see Limits and integration styles.
