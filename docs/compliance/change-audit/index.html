Compliance and audit

Change audit reports

Document every change of a release or a deployment, with who wrote, integrated and approved it, its risk and its environments, in a fingerprinted report.

Edit on GitHub

The change audit report lists every change of a range (one release, two environments, or what the next deployment would bring) with who wrote it, who integrated it, whether it went through a pull request and who approved it, its risk factors and the environments that run it. Use it as evidence for release reviews, change-management audits and incident investigations.

Evidence for change management

The report documents facts from Git and from your hosting service; it does not judge them. Changes without a pull request, without approval or with high risk are counted and listed so that a reviewer can look at them. How you act on them is part of your change and release policy.

Summary

Changes, via pull request, without pull request, direct commits, approved, not approved, review unknown, high risk, reverts and authors. The JSON format also has medium risk, integrators and the first and last integration dates.

Needs attention

The HTML report lists first the changes that are high risk, not approved or without a pull request, then all changes.

Each change

FieldContent
DateWhen the change entered the branch (integration date)
ChangeTitle, pull request number and link, merged branch, head commit
Linked issuesIssues linked to the pull request (with a connection)
CommitsEvery commit of the change: SHA, subject, author, date
SizeFiles changed, lines added and removed
IntegratorWho merged or committed the change into the branch
ReviewReview state and the people who approved
RiskLevel (low, medium, high) and the factors behind it
EnvironmentsThe environments that already run the change

Review states

StateMeaning
ApprovedThe pull request has at least one approval on the hosting service
Not approvedThe pull request was merged without an approval
Unknown (not connected)The change went through a pull request, but approvals could not be read because the hosting service is not connected
No pull requestA direct commit or a local merge: no review is recorded

Approvals need a connection

Who approved a pull request is stored by GitHub, GitLab or Azure DevOps, not by Git. Connect the hosting service before you export (see Connections); otherwise approvals are reported as “unknown” and the report says so in its header. The command line never connects to a hosting service, so its reports always show approvals as unknown.

Risk factors

Every change gets a score from what it changed and how it entered the branch. A score of 5 or more is high, 2 to 4 is medium, below 2 is low. The level is a hint for reviewers, not a verdict.

In VS Code you can replace the sensitive areas and the test file patterns with your own conventions: mergecat.risk.sensitiveAreas and mergecat.risk.testPatterns (see VS Code settings).

Fingerprint

The report carries a SHA-256 fingerprint of the facts it reports: the branch, the base, the tip commit and, for each change, its head commit, its commits, the review state, the approvers, the risk level and the environments. The generation time is not part of it.

  • Regenerating the report on the same history with the same data (approvals, environments, risk rules) gives the same fingerprint. Any change in these facts gives a different one.
  • The HTML report shows it in the footer, the Markdown report in the header and the JSON report in the fingerprint field. The CSV format has no fingerprint.
  • The fingerprint is a checksum, not a digital signature: anyone with the same data can compute it. To detect later changes to a report, store the fingerprint separately, for example in the release ticket or the change record.

Formats

FormatBest forContent
HTMLReading, printing, PDFHeader, summary cards, “needs attention”, all changes with risk factors and commits, fingerprint in the footer. Open it in a browser and print it to PDF (the print layout is A4 landscape).
MarkdownWikis, pull requests, ticketsHeader with fingerprint, summary table, one row per change
CSVSpreadsheetsOne row per change with the columns integration_date, entry_type, head_sha, title, branch, pr_number, pr_url, integrator, authors, commits, review, approved_by, linked_issues, risk, risk_factors, files, lines_added, lines_removed, environments. Cells that start with =, +, - or @ get a leading apostrophe so that spreadsheets do not run them as formulas.
JSONOther tools, archivesEverything: header, summary, every change with its commits, statistics, risk factors and environments, and the fingerprint

Produce a report

What the next deployment would bring. On the Deployments page Needs a connection, choose the environment under Live in (for example production) and what to Compare with (another environment, or the main branch). Then open Export audit report… and choose the format. The report covers exactly the changes listed on the page.

Compare environments: deploying staging to production brings three changesets. Export audit report… documents exactly these.

Any range. Open the Audit report dialog from the Audit button in the toolbar of the History page, from the Export menu (Audit report…), or from File › Audit Report…. Choose which changes:

  • Current view: the branch, base and filters of the History page;
  • Between two releases: what entered after the first tag, branch or commit, up to the second;
  • Between two environments: what deploying one environment (or the default branch) onto another would bring Needs a connection;
  • Not yet in an environment: what the next deployment of the current branch would bring Needs a connection.

Pick HTML, Markdown, CSV or JSON and click Export…. The save dialog suggests your Documents folder. A notification summarises the report (changes, without pull request, high risk, not approved) and offers to open it.

The Audit report dialog: two releases, HTML. The notification summarises the saved report.

When the repository’s hosting service is not connected, the dialog explains that approvals will be reported as “unknown” and offers Connect or Continue without.

Without a connection: connect first, or continue with approvals reported as unknown.

The desktop app does not fill the Environments column of the report; VS Code and the command line do.

Command. Run mergecat: Export Audit Report… from the Command Palette or from the … menu of the Changesets view, then choose the scope:

  • the current view;
  • Between two releases… (tags, branches or commits);
  • Between two environments… (the same choice as on the Deployments page);
  • Not yet in an environment.

Choose the format (HTML, Markdown, CSV or JSON) and where to save the file. The save dialog suggests the repository folder: choose another folder if the report should not end up in the repository. A notification summarises the report and offers to open it.

Deployments page. Open Deployments, use Compare environments and click Export audit report… to document exactly the changes the next deployment would bring.

When the hosting service is not connected, the command first warns that approvals will be reported as “unknown” and offers Connect or Continue without.

The Environments column lists the environments configured in mergecat.environments.definitions, the ones detected from branch and tag names, and, with a connection, the latest deployments of the hosting service.

# Everything that entered main since v1.1.0, as HTML
node packages/core/dist/cli.cjs --repo ~/src/web-shop --audit --base v1.1.0 --format html > audit.html

# With environments: Production runs the newest tag matching v*, Staging runs origin/staging
node packages/core/dist/cli.cjs --repo ~/src/web-shop --audit --base v1.1.0 \
  --env 'Production=tag:v*' --env 'Staging=origin/staging' --format json > audit.json
FlagEffect
--auditPrints the audit report instead of the history
--base <ref>Only what entered after this tag, branch or commit
--env Name=refAn environment that runs a branch or tag; repeatable
--env Name=tag:patternAn environment that runs the newest tag matching the pattern
--formathtml (default for --audit), markdown, csv or json
--since, --until, --grep, --authorFilter the changes

Quote the --env values: shells expand *. The command line reads Git only, so approvals are always unknown. See Command line for every flag.

A routine for releases

  1. Before deploying, open Compare environments and review what the deployment will bring.
  2. Export the report as HTML for people and JSON for the archive, with the hosting service connected.
  3. Look at the “needs attention” section: changes without a pull request, not approved or high risk.
  4. Store both files with the release documentation and write the fingerprint into the release or change ticket.
