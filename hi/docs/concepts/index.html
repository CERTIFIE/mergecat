mergecat कैसे काम करता है

mergecat किसी ब्रांच के Git इतिहास को चेंजसेट में कैसे बदलता है, मर्ज की गई ब्रांच के नाम कैसे पता करता है, और स्क्वैश, रीबेस और दूसरे इंटीग्रेशन स्टाइल को कैसे संभालता है।

GitHub पर एडिट करें

AI की मदद से अंग्रेज़ी से अनूदित। संदेह होने पर अंग्रेज़ी संस्करण मान्य है।

mergecat अपनी ओर से कोई संरचना नहीं गढ़ता: वह जो कुछ दिखाता है, वह कमिट ग्राफ़, कमिट संदेशों और, कनेक्ट होने पर, होस्टिंग सेवा की पुल रिक्वेस्ट से आता है। यह पेज नियम समझाता है, ताकि आप अनुमान लगा सकें कि आपको क्या दिखेगा, और पहचान सकें कि कब कोई इतिहास इन नियमों का पालन नहीं करता।

first-parent पथ पर चलना

जब आप किसी फ़ीचर को main में मर्ज करते हैं, तो मर्ज कमिट दो पैरेंट दर्ज करता है: पहला वह कमिट है जिस पर main था, दूसरा फ़ीचर का सिरा (tip)। किसी ब्रांच के सिरे से केवल पहले पैरेंट को फ़ॉलो करने पर उसकी मेनलाइन मिलती है: वे अवस्थाएँ, क्रम से, जिनसे ब्रांच ख़ुद गुज़री।

mergecat इस first-parent शृंखला पर, नवीनतम कमिट से शुरू करके, चलता है और उस पर के हर कमिट को एक एंट्री में बदलता है:

मेनलाइन पर कमिटएंट्री
एक पैरेंटएक डायरेक्ट कमिट: सीधे ब्रांच पर किया गया, एक पंक्ति।
दो या अधिक पैरेंटएक इंटीग्रेशन (चेंजसेट): एक मर्ज, जो उसके लाए कमिट के साथ एक समूह के रूप में दिखाया जाता है।

एक इंटीग्रेशन में क्या होता है

पैरेंट P1, P2..Pn वाले मर्ज M के समूह में वे कमिट होते हैं जिन तक P2..Pn से पहुँचा जा सकता है, लेकिन P1 से नहीं। Git की भाषा में:

git log P2..Pn ^P1

ये ठीक वही कमिट हैं जो M के ज़रिए ब्रांच में आए। इस उदाहरण में, M पर feature को मर्ज करने से C और D आते हैं:

main      A───B───────M
               \     /
feature         C───D

फ़ॉरवर्ड इंटीग्रेशन

फ़ीचर ब्रांच अक्सर अप-टू-डेट रहने के लिए main को वापस अपने अंदर मर्ज करती हैं (“merge main into feature”)। इस तरह main से आए कमिट तक P1 से पहुँचा जा सकता है, इसलिए उन्हें फ़ीचर के समूह में दोबारा नहीं गिना जाता। “merge main into feature” वाले कमिट ख़ुद डिफ़ॉल्ट रूप से छिपे रहते हैं: वे ब्रांच में कुछ नया नहीं लाए।

उन्हें देखने के लिए फ़िल्टर में फ़ॉरवर्ड-इंटीग्रेशन मर्ज छिपाएँ बंद करें। तब वे समूह के अंदर फ़ॉरवर्ड इंटीग्रेशन चिप के साथ दिखते हैं।

नेस्टेड मर्ज

जब फ़ीचर A को फ़ीचर B में मर्ज किया जाता है, और B को main में, तो A, B के चेंजसेट के अंदर एक उप-समूह बन जाता है, जिस पर नेस्टेड मर्ज का निशान होता है। A के कमिट देखने के लिए उसे विस्तृत करें।

ऑक्टोपस मर्ज

एक साथ तीन या अधिक ब्रांच के मर्ज को ऑक्टोपस फ़्लैग मिलता है। उसके समूह में हर मर्ज की गई ब्रांच की एक लेन होती है, जिसके शीर्ष पर ब्रांच का नाम होता है, और ब्रांच / PR कॉलम नामों को + से जोड़ता है।

खाली मर्ज

जो मर्ज ऐसा कोई कमिट नहीं लाया जो पहले से ब्रांच पर न हो, उसे खाली फ़्लैग मिलता है।

मर्ज की गई ब्रांच का नाम पता करना

Git कमिट में ब्रांच के नाम संग्रहीत नहीं करता। mergecat इस क्रम में नाम ढूँढता है और उस पहले स्रोत पर रुक जाता है जिसमें नाम मिल जाता है:

  1. मर्ज संदेश। ऑफ़लाइन काम करता है और ब्रांच हटाए जाने के बाद भी बना रहता है।
  2. होस्टिंग सेवा की पुल रिक्वेस्ट (कनेक्टेड मोड)। ब्रांच हटाए जाने के बाद भी काम करती है।
  3. ऐसी ब्रांच जो अब भी मर्ज किए गए कमिट की ओर इशारा करती है, लोकल या रिमोट।
  4. मर्ज किए गए कमिट का छोटा SHA, जब और कुछ ज्ञात न हो।

किस स्रोत का उपयोग हुआ, यह देखने के लिए ब्रांच चिप पर होवर करें; विवरण पैनल इसे ब्रांच के नीचे दिखाता है। जब नाम अज्ञात हो और कनेक्ट करने से वह पता चल सकता हो, तो चिप पर ताले का आइकन दिखता है।

ये मर्ज संदेश पहचाने जाते हैं:

किसने लिखासंदेशmergecat क्या पढ़ता है
git mergeMerge branch 'feature/x' into main, Merge branches 'a', 'b' and 'c'ब्रांच के नाम
git pullMerge branch 'x' of https://…ब्रांच का नाम
रिमोट ब्रांच का git mergeMerge remote-tracking branch 'origin/x'रिमोट के बिना ब्रांच का नाम
किसी टैग का git mergeMerge tag 'v1.2.0'टैग का नाम
GitHubMerge pull request #12 from org/feature-xपुल रिक्वेस्ट नंबर और ब्रांच
GitLabMerge branch 'x' into 'main', मुख्य भाग में See merge request group/project!12 के साथब्रांच, मर्ज रिक्वेस्ट नंबर और शीर्षक
BitbucketMerged in feature-x (pull request #12)ब्रांच और पुल रिक्वेस्ट नंबर
Azure DevOpsMerged PR 12: Titleकेवल पुल रिक्वेस्ट नंबर और शीर्षक

एक तरीका जिससे नाम पढ़ने योग्य बने रहते हैं

पुल रिक्वेस्ट को मर्ज कमिट (नो-फ़ास्ट-फ़ॉरवर्ड) के साथ पूरा करें और पुल रिक्वेस्ट के शीर्षक में ब्रांच का नाम या वर्क आइटम ID डालें। शीर्षक मर्ज संदेश में पहुँच जाता है और ब्रांच हटाए जाने के बाद भी बना रहता है।

इंटीग्रेशन स्टाइल

आपकी टीम पुल रिक्वेस्ट कैसे पूरी करती है, इससे तय होता है कि इतिहास में क्या होगा। mergecat हर स्टाइल को उतनी सटीकता से दिखाता है जितनी ग्राफ़ अनुमति देता है, और बताता है कि कब ग्रुपिंग अधूरी है।

पुल रिक्वेस्ट कैसे पूरी की जाती हैंmergecat क्या दिखाता है
मर्ज कमिट (नो-फ़ास्ट-फ़ॉरवर्ड), Azure DevOps के semi-linear merge सहितसमूह।
स्क्वैशएक कमिट। जब संदेश पुल रिक्वेस्ट जैसा दिखता है (Title (#12), Merged PR 12: Title, Bitbucket का Merged in), तो स्क्वैश फ़्लैग लगता है। कनेक्टेड: स्क्वैश-मर्ज PR फ़्लैग लगता है, और विवरण पैनल मूल कमिट की सूची दिखाता है।
रीबेस और फ़ास्ट-फ़ॉरवर्डडायरेक्ट कमिट। कनेक्टेड: हर पुल रिक्वेस्ट के अनुसार रीबेस-मर्ज PR के रूप में समूहित।
ऐसे फ़ीचर का फ़ास्ट-फ़ॉरवर्ड जिसमें फ़ॉरवर्ड इंटीग्रेशन हुआ था, या ब्रांच पर ही git pull वाले मर्जउलटा फ़्लैग: वहाँ से first-parent पथ गलत पक्ष पर जा सकता है (“foxtrot” मर्ज)।
शैलो क्लोनएक चेतावनी; समूह अधूरे हो सकते हैं। जिस कमिट पर इतिहास कटता है, उस पर शैलो फ़्लैग लगता है।

जब इनमें से कोई स्थिति ब्रांच को प्रभावित करती है, तो सूची के ऊपर एक चेतावनी बार दिखती है:

चेतावनीकब
इस ब्रांच में कोई मर्ज कमिट नहीं हैहर एंट्री डायरेक्ट कमिट है, आमतौर पर रीबेस या फ़ास्ट-फ़ॉरवर्ड मर्ज के कारण। उन्हें समूहित करने के लिए होस्टिंग सेवा कनेक्ट करें।
यह ब्रांच नो-फ़ास्ट-फ़ॉरवर्ड मर्ज से इंटीग्रेट नहीं होतीकोई मर्ज नहीं, और पुल रिक्वेस्ट स्क्वैश-मर्ज की हुई लगती हैं।
मिश्रित इंटीग्रेशन तरीकेसामान्य मर्ज के बीच कुछ पुल रिक्वेस्ट स्क्वैश-मर्ज की हुई लगती हैं।
N merge(s) merged "main" into something elseएक या अधिक उलटे मर्ज।
यह एक शैलो क्लोन हैपूरे परिणामों के लिए git fetch --unshallow चलाएँ।

हर सीमा और उससे बचने के तरीके के बारे में अधिक जानकारी: सीमाएं और इंटीग्रेशन स्टाइल।

परफ़ॉर्मेंस

mergecat हर मर्ज के लिए अलग Git प्रोसेस शुरू नहीं करता। यह ब्रांच का पूरा इतिहास एक git log से पढ़ता है, फिर समूह मेमोरी में निकालता है: यह सबसे पुराने कमिट से first-parent शृंखला पर चलता है और हर मर्ज को वे कमिट अपने नाम करने देता है जिन पर अभी किसी का दावा नहीं है। लागत कमिट की संख्या के साथ रैखिक रूप से बढ़ती है; 11,000 कमिट का इतिहास एक सेकंड से काफ़ी कम समय में इंडेक्स हो जाता है। सूची का हेडर दिखाता है कि पिछली बार पढ़ने में कितना समय लगा (read in … ms)।

बाकी काम ज़रूरत पड़ने पर होता है:

  • जब आप कोई पंक्ति चुनते हैं, तब डिफ़ git diff से निकाले जाते हैं;
  • पुल रिक्वेस्ट का डेटा (कनेक्टेड) उन एंट्री के लिए लोड होता है जिन्हें आप देख रहे हैं, और हर कमिट SHA के अनुसार कैश होता है, इसलिए वह फ़ेच के बाद भी मान्य रहता है;
  • हाल ही में पढ़े गए इतिहास मेमोरी में रहते हैं, इसलिए ऐसी ब्रांच पर वापस जाना तुरंत होता है जिसका सिरा नहीं बदला।

सूची और ग्राफ़

इतिहास पेज एक ही इतिहास को दो लेआउट में दिखाता है:

  • सूची: चेंजसेट, ऐसे इंटीग्रेशन के साथ जिन्हें विस्तृत करके आप उनके लाए कमिट देख सकते हैं।
  • ग्राफ़: हर कमिट अपनी लेन के साथ, git log --graph की तरह, पूरे इतिहास के लिए एक बार निकाला गया। हर कमिट पर एक चिप होती है, जो बताती है कि कौन-सा चेंजसेट उसे ब्रांच में लाया; जिस कमिट ने चेंजसेट को इंटीग्रेट किया, उस पर चिप हाइलाइट होती है।

ग्राफ़ लेआउट: हर कमिट, उसके चेंजसेट के साथ टैग किया हुआ।

डिज़ाइन से रीड-ओनली

mergecat ऐसे Git कमांड चलाता है जो केवल पढ़ते हैं। यह केवल तभी लिखता है जब आप ख़ुद कोई कार्रवाई शुरू करते हैं:
