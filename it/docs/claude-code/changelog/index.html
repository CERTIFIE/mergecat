Changelog

Scrivi un changelog Keep a Changelog con /mergecat:changelog, per le modifiche non ancora rilasciate, una versione, tutte le release o qualsiasi intervallo di tag, date e commit.

Modifica su GitHub

Tradotta dall'inglese con l'aiuto dell'IA. In caso di dubbio fa fede la versione inglese.

/mergecat:changelog trasforma ciò che è entrato nel branch principale in un changelog nel formato Keep a Changelog. Ogni pull request integrata, merge o commit diretto è un changeset, già ordinato nelle sezioni (Added, Changed, Deprecated, Removed, Fixed, Security); Claude riscrive la bozza per le persone che usano il tuo progetto. Il risultato è un documento della conversazione, in inglese e in Markdown, salvo diversa richiesta.

Prima la domanda di conformità

In una nuova sessione di Claude Code, il primo changelog inizia con la domanda di conformità (account Claude Team o Enterprise; in caso contrario, la conoscenza dell’AI Act UE, il regolamento europeo sull’intelligenza artificiale, e della direttiva NIS2). La risposta viene registrata sul tuo computer. Vedi Registri di utilizzo dell’AI.

Uso

/mergecat:changelog [from..to | version | all] [pdf] [lang:<code>] [update file]

Puoi anche chiedere con parole tue, per esempio “changelog da v1.2.0 a oggi” o “note di rilascio della v1.3.0 in tedesco come PDF”.

Argomenti

ArgomentoChangelog
(nessuno)Le novità dall’ultima release, come ## [Unreleased]
from..toSolo quell’intervallo; vedi Intervalli
1.4.0 (una versione)Le modifiche non ancora rilasciate come ## [1.4.0] - <today>
allTutte le release dai tag di versione (fino a 20), con l’intestazione di Keep a Changelog
pdfUn documento PDF invece di Markdown; anche “come PDF”, “in PDF”, format:pdf
md, markdownMarkdown, il formato predefinito
lang:<code>La lingua del changelog, es. lang:it; anche a parole, “in italiano”
update fileAggiorna anche il CHANGELOG.md del progetto; vale anche quando chiedi a parole di aggiornare o scrivere CHANGELOG.md

Qualsiasi altra parola è un’istruzione per il testo, per esempio il pubblico o il livello di dettaglio (“per gli utenti finali”, “includi le modifiche interne”).

Intervalli

Ogni estremo di un intervallo è un tag, una data o un commit, in qualsiasi combinazione. Le parentesi quadre sono ammesse ([v1.2.0..v1.3.0]) e un estremo può essere lasciato aperto.

IntervalloModifiche
v1.2.0..v1.3.0La release v1.3.0
v1.2.0..2026-03-31Dopo la v1.2.0, fino alla fine del 31 marzo 2026
2026-01-01..v1.3.0Dal 1º gennaio 2026 (incluso) fino alla v1.3.0
2026-01-01..2026-03-31Ciò che è entrato nel branch nel primo trimestre
v1.2.0..abc1234, 2026-01-01..abc1234Fino a quel commit
abc1234..v1.3.0, abc1234..2026-03-31, abc1234..def5678Dopo quel commit
v1.3.0..Fino all’ultima modifica
..v1.0.0Dal primo commit
  • L’inizio è escluso e la fine è inclusa.
  • Una data si riferisce a quando una modifica è entrata nel branch principale (cronologia first-parent), nel fuso orario locale del tuo computer. Come inizio significa “da quel giorno in poi”, come fine “fino alla fine di quel giorno”.
  • Le date sono nel formato YYYY-MM-DD, facoltativamente con un’ora e un fuso orario (2026-03-31T18:00, 2026-03-31 18:00+02:00).
  • Un commit è uno SHA o un nome di branch.
  • Se un nome è sia un tag sia una data, vince il tag. Gli estremi invertiti vengono segnalati, e Claude ti dice come è stato risolto ogni estremo.
  • Un estremo sconosciuto o una data non valida vengono spiegati in una riga, con estremi validi suggeriti a partire dai tag; Claude non tira a indovinare.

Esegui /mergecat:tags per vedere i tag e gli intervalli pronti all’uso.

Lingua

  • Il changelog è in inglese, a meno che tu non chieda un’altra lingua con lang:<code> o a parole. Scrivere la richiesta in un’altra lingua non equivale a chiedere quella lingua.
  • Il titolo, il preambolo, le intestazioni delle sezioni e “Unreleased” sono già tradotti per inglese, italiano, tedesco, francese e spagnolo (en, it, de, fr, es). Per le altre lingue li traduce Claude.
  • Claude scrive ogni riga di modifica nella lingua richiesta. Versioni, date, link alle pull request, riferimenti alle issue, identificatori di codice e nomi di file restano invariati.
  • Quando chiedi di aggiornare un CHANGELOG.md scritto in una lingua diversa da quella richiesta (o dall’inglese, se non ne hai chiesta una), Claude chiede una volta quale lingua usare.

Formato

Markdown è il formato predefinito. Chiedi il PDF (pdf, “come PDF”) quando ti serve: Claude prepara il Markdown finale, lo converte con lo strumento render_pdf e ti consegna il file, chiamato changelog-<repository>-<version or range>.pdf. Il PDF viene scritto fuori dal tuo progetto (nello scratchpad di Claude o nella cartella temporanea di sistema).

I PDF sono in formato A4 e usano i font PDF standard (Helvetica, Courier):

  • il testo Latin-1, che copre le lingue dell’Europa occidentale, viene stampato così com’è;
  • alcuni caratteri tipografici diventano ASCII: → diventa ->, le virgolette curve diventano virgolette dritte, … diventa ..., € diventa EUR;
  • i caratteri di altri sistemi di scrittura (greco, cirillico, cinese, giapponese, …) e le emoji vengono sostituiti con ?. Per le lingue scritte con altri sistemi di scrittura usa Markdown.

Il PDF supporta titoli, paragrafi, elenchi, citazioni, linee orizzontali, codice, tabelle semplici, grassetto, corsivo e link. Il CHANGELOG.md del progetto è sempre in Markdown.

Dove finisce il changelog

Il changelog è un documento della conversazione. Claude lo pubblica come artifact Markdown o lo invia come file che puoi aprire e scaricare (changelog-<repository>-<version or range>.md), oppure lo mostra come blocco Markdown nella risposta. Nel tuo repository non viene scritto nulla.

Solo con update file, o quando lo chiedi a parole, Claude aggiorna anche CHANGELOG.md nella radice del repository:

  • ogni sezione di release esistente resta esattamente com’è;
  • le modifiche vanno in ## [Unreleased], oppure sotto una nuova intestazione di versione posta sotto di essa, seguita da un ## [Unreleased] vuoto;
  • i riferimenti dei link in fondo al file vengono aggiornati;
  • se il file non esiste, Claude lo crea con l’intestazione di Keep a Changelog;
  • un intervallo che non è una release (termina con una data o un commit) non entra in CHANGELOG.md: Claude lo segnala e consegna solo il documento.

Claude legge sempre prima un CHANGELOG.md esistente (in sola lettura). Quando la sua versione più recente è più vecchia del tag di versione più recente, il changelog include anche le release che mancano nel file.

Come Claude rielabora la bozza

Gli strumenti di mergecat restituiscono una bozza e dati strutturati per ogni changeset: la sezione e il motivo per cui è stata scelta, numero e link della pull request, branch, commit e i flag breaking e internal. Claude poi:

  • scrive una riga per ogni modifica visibile agli utenti, pensata per gli utenti, mantenendo i link alle pull request e i riferimenti alle issue;
  • descrive le voci vaghe (“Merge branch …”) a partire dai loro commit;
  • mantiene i marcatori BREAKING e mette le breaking change per prime nella loro sezione;
  • tralascia le voci interne (documentazione, test, CI, attività varie), a meno che non siano rilevanti per gli utenti o che tu abbia chiesto tutto;
  • corregge una sezione quando il motivo indicato nei dati è chiaramente sbagliato, e unisce i duplicati;
  • non aggiunge mai una modifica che non sia nell’output degli strumenti.

Alla fine, Claude riassume la release o l’intervallo e come è stato risolto ogni estremo, la lingua e il formato, il numero di modifiche per sezione e tutto ciò che richiede una tua decisione: una sezione poco chiara, una modifica senza pull request, una breaking change, estremi invertiti. Rivedi il changelog prima di pubblicarlo.

Dati delle pull request

Senza token, il changelog si basa sui dati Git: messaggi di merge, nomi dei branch e oggetti dei commit, e Claude dice in una riga che per i titoli delle pull request serve GITHUB_TOKEN. Per i repository su github.com, avvia Claude Code con GITHUB_TOKEN (o GH_TOKEN) impostato su un token che può leggere le pull request del repository: righe e sezioni derivano allora da titoli, etichette e issue collegate delle pull request. Vedi Dati delle pull request.

Se la cronologia non ha commit di merge o usa squash merge, Claude dice che il raggruppamento si basa sui messaggi dei commit; vedi Limiti e stili di integrazione.
