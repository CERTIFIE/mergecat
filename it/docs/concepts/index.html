Come funziona mergecat

Come mergecat trasforma la cronologia Git di un branch in changeset, dà un nome ai branch integrati e gestisce squash, rebase e gli altri stili di integrazione.

Modifica su GitHub

Tradotta dall'inglese con l'aiuto dell'IA. In caso di dubbio fa fede la versione inglese.

mergecat non inventa alcuna struttura: tutto ciò che mostra viene dal grafo dei commit, dai messaggi di commit e, se connesso, dalle pull request del servizio di hosting. Questa pagina spiega le regole, così puoi prevedere cosa vedrai e riconoscere quando una cronologia non le segue.

Il percorso first-parent

Quando esegui il merge di una feature in main, il commit di merge registra due genitori: il primo è il commit su cui si trovava main, il secondo è la punta della feature. Seguendo solo i primi genitori dalla punta di un branch si ottiene la sua mainline: la sequenza degli stati attraversati dal branch stesso.

mergecat percorre questa catena di primi genitori (first-parent), dal più recente, e trasforma ogni commit che vi si trova in una voce:

Commit sulla mainlineVoce
Un genitoreUn commit diretto: fatto sul branch stesso, una riga.
Due o più genitoriUn’integrazione (changeset): un merge, mostrato come gruppo con i commit che ha portato.

Cosa contiene un’integrazione

Per un merge M con genitori P1, P2..Pn, il gruppo contiene i commit raggiungibili da P2..Pn ma non da P1. In termini Git:

git log P2..Pn ^P1

Sono esattamente i commit entrati nel branch tramite M. In questo esempio, il merge di feature in M porta C e D:

main      A───B───────M
               \     /
feature         C───D

Forward integration

Spesso i feature branch integrano di nuovo main per restare aggiornati (“merge di main nella feature”). I commit arrivati da main in questo modo sono raggiungibili da P1, quindi non vengono contati di nuovo nel gruppo della feature. I commit di “merge di main nella feature” sono nascosti per impostazione predefinita: non hanno portato nulla di nuovo nel branch.

Disattiva Nascondi i merge di forward integration in Filtri per vederli. Compaiono allora dentro il gruppo con un chip forward integration.

Merge annidati

Quando la feature A viene integrata nella feature B, e B in main, A diventa un sottogruppo dentro il changeset di B, contrassegnato come Merge annidato. Espandilo per vedere i commit di A.

Merge octopus

Un merge di tre o più branch contemporaneamente riceve il flag octopus. Il suo gruppo ha una linea per ogni branch integrato, ciascuna con il nome del branch in testa, e la colonna Branch / PR unisce i nomi con +.

Merge vuoti

Un merge che non ha portato alcun commit che non fosse già sul branch riceve il flag vuoto.

Il nome del branch integrato

Git non memorizza i nomi dei branch nei commit. mergecat cerca il nome in quest’ordine e si ferma alla prima fonte che lo contiene:

  1. Il messaggio di merge. Funziona offline e sopravvive all’eliminazione del branch.
  2. La pull request del servizio di hosting (modalità connessa). Funziona anche dopo che il branch è stato eliminato.
  3. Un branch che punta ancora al commit integrato, locale o remoto.
  4. Lo SHA breve del commit integrato, quando non si sa nient’altro.

Passa il mouse su un chip di branch per vedere quale fonte è stata usata; il pannello dei dettagli la mostra sotto Branch. Quando il nome è sconosciuto e la connessione lo risolverebbe, il chip mostra un’icona a forma di lucchetto.

Questi messaggi di merge vengono riconosciuti:

Scritto daMessaggioCosa legge mergecat
git mergeMerge branch 'feature/x' into main, Merge branches 'a', 'b' and 'c'Nomi dei branch
git pullMerge branch 'x' of https://…Nome del branch
git merge di un branch remotoMerge remote-tracking branch 'origin/x'Nome del branch senza il remote
git merge di un tagMerge tag 'v1.2.0'Nome del tag
GitHubMerge pull request #12 from org/feature-xNumero della pull request e branch
GitLabMerge branch 'x' into 'main' con See merge request group/project!12 nel corpoBranch, numero e titolo della merge request
BitbucketMerged in feature-x (pull request #12)Branch e numero della pull request
Azure DevOpsMerged PR 12: TitleSolo numero e titolo della pull request

Una convenzione che mantiene leggibili i nomi

Completa le pull request con un commit di merge (no fast-forward) e metti il nome del branch o l’ID del work item nel titolo della pull request. Il titolo finisce nel messaggio di merge e sopravvive all’eliminazione del branch.

Stili di integrazione

Il modo in cui il tuo team completa le pull request decide cosa contiene la cronologia. mergecat mostra ogni stile nel modo più fedele che il grafo consente e segnala quando il raggruppamento è incompleto.

Come vengono completate le pull requestCosa mostra mergecat
Commit di merge (no fast-forward), compreso il merge semi-lineare di Azure DevOpsGruppi.
SquashUn solo commit. Con il flag squash quando il messaggio sembra quello di una pull request (Title (#12), Merged PR 12: Title, il Merged in di Bitbucket). Se connesso: flag PR con squash merge, e il pannello dei dettagli elenca i commit originali.
Rebase e fast-forwardCommit diretti. Se connesso: raggruppati per pull request come PR con rebase merge.
Fast-forward di una feature che ha usato la forward integration, o merge da git pull sul branch stessoFlag invertito: da lì il percorso first-parent potrebbe seguire il lato sbagliato (merge “foxtrot”).
Clone shallowUn avviso; i gruppi potrebbero essere incompleti. Il commit in cui la cronologia si interrompe ha il flag shallow.

Quando una di queste situazioni riguarda il branch, sopra l’elenco compare una barra di avviso:

AvvisoQuando
Questo branch non ha commit di mergeOgni voce è un commit diretto, di solito per merge con rebase o fast-forward. Connetti il servizio di hosting per raggrupparli.
Questo branch non è integrato con merge no-fast-forwardNessun merge, e le pull request sembrano integrate con squash merge.
Stili di integrazione mistiAlcune pull request sembrano integrate con squash merge tra merge normali.
N merge(s) merged "main" into something else (in italiano: N merge ha/hanno portato “main” in qualcos’altro)Uno o più merge invertiti.
Questo è un clone shallowEsegui git fetch --unshallow per avere risultati completi.

Altro su ciascun limite e su come evitarlo: Limiti e stili di integrazione.

Prestazioni

mergecat non avvia un processo Git per ogni merge. Legge l’intera cronologia del branch con un solo git log, poi calcola i gruppi in memoria: percorre la catena first-parent dal commit più vecchio e lascia che ogni merge rivendichi i commit non ancora rivendicati. Il costo cresce in modo lineare con il numero di commit; una cronologia di 11.000 commit viene indicizzata in molto meno di un secondo. L’intestazione dell’elenco mostra quanto ha richiesto l’ultima lettura (read in … ms, in italiano “letta in … ms”).

Il resto del lavoro avviene su richiesta:

  • i diff vengono calcolati con git diff quando selezioni una riga;
  • i dati delle pull request (se connesso) vengono caricati per le voci che stai guardando e memorizzati in cache per SHA del commit, così restano validi da un fetch all’altro;
  • le cronologie lette più di recente restano in memoria, così tornare a un branch la cui punta non si è spostata è immediato.

Elenco e grafo

La pagina Cronologia mostra la stessa cronologia in due layout:

  • Elenco: i changeset, con le integrazioni che puoi espandere fino ai commit che hanno portato.
  • Grafo: ogni commit con le sue linee, come git log --graph, calcolato una volta per l’intera cronologia. Ogni commit ha un chip con il changeset che l’ha portato nel branch; il chip è evidenziato sul commit che l’ha integrato.

Il layout a grafo: ogni commit, etichettato con il suo changeset.

In sola lettura per progettazione

mergecat esegue comandi Git che leggono. Scrive solo quando sei tu ad avviare un’azione:

AzioneCosa viene eseguito
Fetch nella pagina Branchgit fetch --all --tags --prune (i tuoi branch locali non vengono modificati)
Nuovo tag, Pushgit tag, git push <remote> refs/tags/<name>
Nuova pull requestUna chiamata al servizio di hosting

Il fetch e il push dei tag usano le tue credenziali Git (il tuo credential helper); mergecat non chiede mai una password Git.
