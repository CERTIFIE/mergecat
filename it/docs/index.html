Introduzione

mergecat mostra cosa è entrato in un branch Git e quando, raggruppato per integrazione come i changeset di TFS, e segue ogni modifica dal branch fino al deployment.

Modifica su GitHub

Tradotta dall'inglese con l'aiuto dell'IA. In caso di dubbio fa fede la versione inglese.

mergecat raggruppa la cronologia Git di un branch per integrazione, come TFS e TFVC mostravano i changeset. Vedi cosa è entrato in main (o in qualsiasi branch), quando, tramite quale pull request e, in seguito, quale ambiente lo esegue. Funziona su qualsiasi repository locale, offline, e per impostazione predefinita si limita a leggere.

La pagina Cronologia dell'app desktop, connessa a GitHub.

Il problema

git log su main mescola i commit di tutti i feature branch. Dopo qualche merge non riesci più a capire quali commit vanno insieme, quale branch li ha portati o quando sono arrivati davvero su main. A chi viene da Team Foundation Server manca la vista dei changeset: una riga per check-in, con tutto ciò che conteneva.

mergecat ripristina quella vista. Percorre la cronologia first-parent del branch e mostra:

  • i commit diretti fatti sul branch, uno per riga;
  • le integrazioni (commit di merge) come gruppi espandibili, con i commit che hanno portato e il nome del branch integrato con il merge, anche dopo che il branch è stato eliminato.

Connetti GitHub, GitLab o Azure DevOps e mergecat aggiunge ciò che Git non memorizza: pull request, squash e rebase merge, issue collegate, pipeline e deployment. Come funziona mergecat spiega il raggruppamento nel dettaglio.

Tre modi per usarlo

App desktop → macOS, Windows e Linux. Cronologia, branch, tag, pull request, pipeline e deployment in un’unica finestra. Estensione per VS Code → La vista Changesets, le pagine del repository nelle schede dell’editor e i diff nativi, dentro il tuo editor. Plugin per Claude Code → Tag e bozze in formato Keep a Changelog a partire dai changeset, tramite un server MCP in sola lettura.

Uno strumento a riga di comando espone la stessa cronologia, le metriche e i report di audit per gli script: vedi Riga di comando.

Principi

Prima di tutto locale. mergecat legge la cronologia dal tuo clone con il tuo Git. Raggruppamento, diff, filtri, esportazioni, branch e tag funzionano senza account e senza connessione di rete. La connessione al servizio di hosting è facoltativa e aggiunge solo dati.

In sola lettura per impostazione predefinita. mergecat non esegue mai commit, checkout, merge né riscrive nulla. Scrive solo quando sei tu ad avviare un’azione: Fetch, creare o fare il push di un tag, creare una pull request. Il fetch e il push dei tag usano le tue credenziali Git.

Le tue credenziali restano sul tuo computer. I token sono cifrati con il portachiavi di sistema; i dati delle pull request sono memorizzati in cache nella cartella dati dell’app, mai nel repository. mergecat comunica con Git e, se ne connetti uno, con il tuo servizio di hosting. Vedi Solo locale o connesso.

Pensato per gli audit delle modifiche

Sapere cosa è entrato in un branch, chi l’ha approvato e dove è in esecuzione è il cuore di un audit delle modifiche. mergecat lo trasforma in un report.

AI Act UE e NIS2

Il report di audit elenca ogni modifica di un intervallo: chi l’ha scritta, chi l’ha integrata, se è passata da una pull request e chi l’ha approvata, i suoi fattori di rischio e gli ambienti che la eseguono, con un’impronta SHA-256 del contenuto. Il plugin per Claude Code registra, una volta per sessione, se usi un account Claude Team o Enterprise prima di leggere un repository. Leggi AI Act UE e NIS2 per vedere come queste registrazioni supportano i tuoi obblighi di documentazione.

Esplora la documentazione

Installazione → Installa l’app desktop su macOS, Windows o Linux. Guida rapida → Apri un repository e leggi i suoi changeset in cinque minuti. Come funziona mergecat → Percorso first-parent, nomi dei branch, squash e rebase merge. Cronologia: changeset e grafo → Ogni parte della pagina Cronologia dell’app desktop. Solo locale o connesso → Cosa aggiunge la connessione a GitHub, GitLab o Azure DevOps. Report di audit delle modifiche → Chi ha scritto, revisionato e approvato ogni modifica di una release.
