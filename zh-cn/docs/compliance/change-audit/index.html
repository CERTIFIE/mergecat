合规与审计

变更审计报告

在带指纹的报告中记录一个发布或一次部署的每项变更，包括由谁编写、集成和批准，它的风险以及运行它的环境。

在 GitHub 上编辑

本页借助 AI 从英文翻译。如有疑问，以英文版本为准。

变更审计报告列出某个范围（一个发布、两个环境之间，或下一次部署会带来的内容）内的每项变更，包括由谁编写、由谁集成、是否经过拉取请求以及由谁批准、它的风险因素，以及运行它的环境。可以将它用作发布评审、变更管理审计和事件调查的证据。

变更管理的证据

报告记录的是来自 Git 和托管服务的事实；它不对这些事实作出判断。没有拉取请求、未获批准或高风险的变更会被统计并列出，以便审阅者查看。如何处理这些变更属于你的变更和发布政策。

报告包含什么

报告头

字段内容
标题例如 Change audit: v1.1.0 → v1.2.0 或 Change audit: staging not yet in production
仓库托管服务上的 owner/name（或文件夹名称）以及远程 URL
分支所分析的分支或提交、与之对比的基准，以及最新提交
周期最早和最新变更的集成日期
拉取请求数据批准信息是来自托管服务，还是未知
环境针对每项变更检查的环境
生成信息日期和时间，以及生成报告的应用
指纹所报告事实的 SHA-256 值（参见指纹）

摘要

变更数、经过拉取请求的变更、没有拉取请求的变更、直接提交、已批准、未批准、审阅情况未知、高风险、还原和作者。JSON 格式还包含中风险、集成者，以及首次和最后一次集成的日期。

需要关注

HTML 报告会首先列出高风险、未批准或没有拉取请求的变更，然后列出所有变更。

每项变更

字段内容
日期变更进入分支的时间（集成日期）
变更标题、拉取请求编号和链接、被合并的分支、头提交
关联的议题关联到拉取请求的议题（需要连接）
提交该变更的每个提交：SHA、主题、作者、日期
规模更改的文件数，以及新增和删除的行数
集成者将该变更合并或提交到分支的人
审阅审阅状态以及批准者
风险级别（低、中、高）及其背后的因素
环境已经在运行该变更的环境

审阅状态

状态含义
已批准（Approved）该拉取请求在托管服务上至少获得了一次批准
未批准（Not approved）该拉取请求在未获批准的情况下被合并
未知（未连接）（Unknown (not connected)）该变更经过了拉取请求，但由于未连接托管服务，无法读取批准信息
无拉取请求（No pull request）直接提交或本地合并：没有记录任何审阅

批准信息需要连接

拉取请求由谁批准是由 GitHub、GitLab 或 Azure DevOps 存储的，而不是由 Git 存储。请在导出之前连接托管服务（参见连接）；否则批准情况会报告为“unknown”，报告也会在报告头中注明这一点。命令行从不连接托管服务，因此其报告始终将批准情况显示为未知。

风险因素

每项变更都会根据其更改的内容和进入分支的方式获得一个分数。5 分及以上为高，2 到 4 分为中，低于 2 分为低。该级别是给审阅者的提示，而不是结论。

因素分数条件
超大变更3更改 1,500 行或以上
大型变更2更改 500 行或以上
文件数量多130 个文件或以上
以删除为主1删除 300 行或以上，且删除行数超过新增行数的两倍
数据库架构或迁移3**/migrations/**、**/*.sql、**/db/migrate/**、Flyway、Liquibase 等文件
构建或部署流水线2.github/workflows/**、azure-pipelines*.yml、.gitlab-ci.yml、Jenkinsfile、bitbucket-pipelines.yml、Fastfile
配置2appsettings*.json、*.config、.env*、application*.yml、application*.properties、*.ini
身份验证、权限或证书2**/auth/**、**/security/**、*.pem、*.pfx、*.key、*.p12 及类似文件
基础设施2Dockerfile*、docker-compose*.yml、*.tf、*.bicep、**/k8s/**、**/helm/**
依赖项1package.json、锁文件、*.csproj、pom.xml、build.gradle*、requirements*.txt、go.mod、Cargo.toml 及类似文件
未更改测试2更改了代码文件，但没有更改任何测试文件
直接提交到分支2没有拉取请求的直接提交
未经拉取请求合并1没有拉取请求的本地合并
在请求更改的情况下合并2拉取请求在被请求更改的情况下被合并（需要连接）
未经批准合并2拉取请求没有获得任何批准（需要连接）

作者众多1超过三位作者
还原之前的变更1主题以“Revert”开头

在 VS Code 中，你可以用自己的约定替换敏感区域和测试文件模式：mergecat.risk.sensitiveAreas 和 mergecat.risk.testPatterns（参见 VS Code 设置）。

指纹

报告附有其所报告事实的 SHA-256 指纹：分支、基准、最新提交，以及每项变更的头提交、其提交、审阅状态、批准者、风险级别和环境。生成时间不包含在内。

  • 基于相同的历史记录和相同的数据（批准、环境、风险规则）重新生成报告，会得到相同的指纹。这些事实的任何变化都会得到不同的指纹。
  • HTML 报告在页脚中显示指纹，Markdown 报告在报告头中显示，JSON 报告则在 fingerprint 字段中提供。CSV 格式没有指纹。
  • 指纹是校验和，而不是数字签名：任何拥有相同数据的人都可以计算出它。要检测报告日后是否被更改，请将指纹单独保存，例如保存在发布工单或变更记录中。

格式

格式最适用于内容
HTML阅读、打印、PDF报告头、摘要卡片、“需要关注”部分、所有变更及其风险因素和提交，页脚中的指纹。在浏览器中打开并打印为 PDF（打印布局为 A4 横向）。
MarkdownWiki、拉取请求、工单带指纹的报告头、摘要表格，每项变更一行
CSV电子表格每项变更一行，列为 integration_date、entry_type、head_sha、title、branch、pr_number、pr_url、integrator、authors、commits、review、approved_by、linked_issues、risk、risk_factors、files、lines_added、lines_removed、environments。以 =、+、- 或 @ 开头的单元格会在开头加上一个撇号，以免电子表格将其作为公式执行。
JSON其他工具、归档全部内容：报告头、摘要、每项变更及其提交、统计信息、风险因素和环境，以及指纹

生成报告

下一次部署会带来什么。 在部署页面 需要连接 上，在已上线于下选择环境（例如 production），并选择要对比的对象（另一个环境或主分支）。然后打开导出审计报告…，并选择格式。报告涵盖的正是页面上列出的变更。

对比环境：将 staging 部署到 production 会带来三个变更集。“导出审计报告…”会准确记录这些变更集。

任意范围。 在“历史记录”页面的工具栏中点击审计按钮、从导出菜单（审计报告…）中选择，或选择文件 › 审计报告…，即可打开审计报告对话框。选择哪些变更：

  • 当前视图：“历史记录”页面的分支、基准和筛选条件；
  • 两个发布之间：在第一个标签、分支或提交之后、截至第二个为止进入的内容；
  • 两个环境之间：将一个环境（或默认分支）部署到另一个环境会带来的内容 需要连接；
  • 尚未进入某个环境：当前分支的下一次部署会带来的内容 需要连接。

选择 HTML、Markdown、CSV 或 JSON，然后点击导出…。保存对话框会建议你的“文档”文件夹。一条通知会汇总报告（变更、无拉取请求、高风险、未批准），并提供打开报告的选项。

“审计报告”对话框：两个发布之间，HTML。通知汇总了已保存的报告。

当仓库的托管服务未连接时，对话框会说明批准情况将报告为“unknown”，并提供连接或不连接，继续。

没有连接时：先连接，或者继续并将批准情况报告为未知。

桌面应用不会填写报告中的“环境”列；VS Code 和命令行会填写。

命令。 从命令面板或 Changesets 视图的 … 菜单中运行 mergecat: Export Audit Report…，然后选择范围：

  • 当前视图；
  • Between two releases…（标签、分支或提交）；
  • Between two environments…（与 Deployments 页面上的选择相同）；
  • 尚未进入某个环境（Not yet in）。

选择格式（HTML、Markdown、CSV 或 JSON）以及保存文件的位置。保存对话框会建议仓库文件夹：如果报告不应放在仓库中，请选择其他文件夹。一条通知会汇总报告，并提供打开报告的选项。

Deployments 页面。 打开 Deployments，使用 Compare environments，然后点击 Export audit report…，即可准确记录下一次部署会带来的变更。

当托管服务未连接时，该命令会先警告批准情况将报告为“unknown”，并提供 Connect 或 Continue without。

报告中的“环境”列会列出在 mergecat.environments.definitions 中配置的环境、根据分支和标签名称检测到的环境，以及（已连接时）托管服务的最新部署。

# Everything that entered main since v1.1.0, as HTML
node packages/core/dist/cli.cjs --repo ~/src/web-shop --audit --base v1.1.0 --format html > audit.html

# With environments: Production runs the newest tag matching v*, Staging runs origin/staging
node packages/core/dist/cli.cjs --repo ~/src/web-shop --audit --base v1.1.0 \
  --env 'Production=tag:v*' --env 'Staging=origin/staging' --format json > audit.json
参数效果
--audit输出审计报告，而不是历史记录
--base <ref>仅包含在此标签、分支或提交之后进入的内容
--env Name=ref运行某个分支或标签的环境；可重复使用
--env Name=tag:pattern运行与该模式匹配的最新标签的环境
--formathtml（--audit 的默认值）、markdown、csv 或 json
--since、--until、--grep、--author筛选变更

请为 --env 的值加上引号：shell 会展开 *。命令行只读取 Git，因此批准情况始终未知。有关每个参数，请参见命令行。

发布例行流程

  1. 部署之前，打开对比环境，审阅此次部署将带来的内容。
  2. 在已连接托管服务的情况下，将报告导出为 HTML（供人阅读）和 JSON（用于归档）。
  3. 查看“需要关注”部分：没有拉取请求、未获批准或高风险的变更。
  4. 将这两个文件与发布文档一起保存，并将指纹写入发布工单或变更工单中。
