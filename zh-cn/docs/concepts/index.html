mergecat 的工作原理

mergecat 如何将分支的 Git 历史记录转换为变更集、如何命名被合并的分支，以及如何处理压缩合并、变基合并和其他集成方式。

在 GitHub 上编辑

本页借助 AI 从英文翻译。如有疑问，以英文版本为准。

mergecat 不会凭空创造结构：它显示的一切都来自提交图、提交消息，以及（连接后）托管服务的拉取请求。本页说明这些规则，让你能够预判将看到的内容，并识别出不遵循这些规则的历史记录。

第一父提交遍历

当你把一个功能分支合并到 main 时，合并提交会记录两个父提交：第一个是 main 当时所在的提交，第二个是功能分支的最新提交。从分支的最新提交出发、只沿着第一父提交前进，就得到了它的主线（mainline）：即分支本身经历过的一系列状态。

mergecat 从新到旧遍历这条第一父提交链，并将链上的每个提交转换为一个条目：

主线上的提交条目
一个父提交一个直接提交：直接在分支上进行，占一行。
两个或更多父提交一个集成（变更集）：一次合并，以分组形式显示，包含它带入的提交。

集成包含什么

对于父提交为 P1, P2..Pn 的合并 M，分组包含可从 P2..Pn 到达、但无法从 P1 到达的提交。用 Git 的术语表示：

git log P2..Pn ^P1

这些正是通过 M 进入分支的提交。在下面的示例中，在 M 处合并 feature 带入了 C 和 D：

main      A───B───────M
               \     /
feature         C───D

正向集成

功能分支经常把 main 合并回来以保持最新（“merge main into feature”）。以这种方式从 main 带来的提交可以从 P1 到达，因此不会在功能分支的分组中被重复计算。这些“merge main into feature”提交本身默认是隐藏的：它们没有给分支带来任何新内容。

在筛选中关闭隐藏正向集成合并即可看到它们。它们随后会出现在分组内，并带有正向集成徽标。

嵌套合并

当功能分支 A 合并到功能分支 B，B 又合并到 main 时，A 会成为 B 的变更集中的一个子分组，标记为嵌套合并。展开它即可看到 A 的提交。

章鱼合并

一次合并三个或更多分支的合并会带有章鱼合并标志。它的分组中，每个被合并的分支各占一条泳道，每条泳道以分支名称开头；分支 / PR 列用 + 连接这些名称。

空合并

如果一次合并没有带入任何分支上尚不存在的提交，它会带有空合并标志。

命名被合并的分支

Git 不会在提交中存储分支名称。mergecat 按以下顺序查找名称，并在第一个包含该名称的来源处停止：

  1. 合并消息。 可离线使用，且分支被删除后依然有效。
  2. 托管服务中的拉取请求（已连接模式）。分支被删除后依然有效。
  3. 仍指向被合并提交的分支，本地分支或远程分支均可。
  4. 被合并提交的短 SHA，在没有其他信息时使用。

将鼠标悬停在分支徽标上，可以查看使用了哪个来源；详细信息窗格会在分支下显示它。当名称未知、而连接后可以解析出名称时，徽标会显示一个锁形图标。

mergecat 可识别以下合并消息：

写入者消息mergecat 读取的内容
git mergeMerge branch 'feature/x' into main、Merge branches 'a', 'b' and 'c'分支名称
git pullMerge branch 'x' of https://…分支名称
合并远程分支的 git mergeMerge remote-tracking branch 'origin/x'不含远程名称的分支名称
合并标签的 git mergeMerge tag 'v1.2.0'标签名称
GitHubMerge pull request #12 from org/feature-x拉取请求编号和分支
GitLabMerge branch 'x' into 'main'，正文中带有 See merge request group/project!12分支、合并请求编号和标题
BitbucketMerged in feature-x (pull request #12)分支和拉取请求编号
Azure DevOpsMerged PR 12: Title仅拉取请求编号和标题

让名称保持可读的约定

使用合并提交（非快进）完成拉取请求，并在拉取请求标题中写上分支名称或工作项 ID。标题会写入合并消息，并在分支被删除后依然保留。

集成方式

团队完成拉取请求的方式决定了历史记录中包含什么。mergecat 会在提交图允许的范围内尽可能如实地显示每种方式，并在分组不完整时给出提示。

拉取请求的完成方式mergecat 显示的内容
合并提交（非快进），包括 Azure DevOps 的半线性合并分组。
压缩合并一个提交。当消息看起来像拉取请求时（Title (#12)、Merged PR 12: Title、Bitbucket 的 Merged in），标记为压缩。已连接时：标记为压缩合并的 PR，并且详细信息窗格会列出原始提交。
变基和快进直接提交。已连接时：按拉取请求分组，显示为变基合并的 PR。
使用过正向集成的功能分支被快进合并，或在分支本身上执行的 git pull 合并标记为反向：从那里开始，第一父提交路径可能会沿着错误的一侧（“foxtrot”合并）。
浅克隆显示警告；分组可能不完整。历史记录被截断处的提交标记为浅克隆。

当分支受到上述某种情况影响时，列表上方会出现一个警告栏：

警告出现时机
此分支没有合并提交每个条目都是直接提交，通常是因为使用了变基或快进合并。连接托管服务即可对它们进行分组。
此分支没有通过非快进合并进行集成没有合并，并且拉取请求看起来是以压缩方式合并的。
集成方式混合在常规合并中，有些拉取请求看起来是以压缩方式合并的。
N merge(s) merged "main" into something else存在一个或多个反向合并。
这是一个浅克隆运行 git fetch --unshallow 以获得完整结果。

关于每项限制以及如何避免的更多信息：限制与集成方式。

性能

mergecat 不会为每次合并启动一个 Git 进程。它通过一次 git log 读取分支的完整历史记录，然后在内存中计算分组：它从最旧的提交开始遍历第一父提交链，让每次合并认领尚未被认领的提交。开销随提交数量线性增长；包含 11,000 个提交的历史记录可在远不到一秒的时间内完成索引。列表标题会显示上一次读取所用的时间（read in … ms）。

其他工作按需进行：

  • 选中某一行时，才使用 git diff 计算差异；
  • 拉取请求数据（已连接时）只为你正在查看的条目加载，并按提交 SHA 缓存，因此在多次获取之间依然有效；
  • 最近读取的历史记录保留在内存中，因此切换回一个最新提交没有移动的分支时，会立即显示。

列表和图形

“历史记录”页面以两种布局显示同一份历史记录：

  • 列表：变更集，其中的集成可以展开，查看它们带入的提交。
  • 图形：每个提交及其泳道，类似 git log --graph，针对整个历史记录计算一次。每个提交都带有一个徽标，显示将它带入分支的变更集；在集成该变更集的提交上，这个徽标会突出显示。

图形布局：每个提交都标有它的变更集。

设计上即为只读

mergecat 运行的是读取类的 Git 命令。只有当你亲自启动操作时它才会写入：

操作运行的内容
“分支”页面上的获取git fetch --all --tags --prune（不会更改你的本地分支）
新建标签、推送git tag、git push <remote> refs/tags/<name>
新建拉取请求调用托管服务

获取和标签推送使用你的 Git 凭据（你的凭据助手）；mergecat 从不索要 Git 密码。
