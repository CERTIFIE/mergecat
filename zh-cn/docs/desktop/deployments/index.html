桌面应用

部署与环境

查看每个环境运行的标签和提交、每次部署带来了什么，以及将一个环境部署到另一个环境会带来什么，并附带发布说明和审计报告。

在 GitHub 上编辑

本页借助 AI 从英文翻译。如有疑问，以英文版本为准。

需要连接

“部署”页面追踪变更离开分支之后的去向：每个环境运行的是哪个版本、何时到达那里、通过哪次流水线运行，以及下一次部署会带来什么。从导航栏中的部署打开它。

此页面需要连接仓库的托管服务；连接之前，页面会提供连接按钮。部署数据来自 GitHub 部署、GitLab 环境和部署，以及 Azure DevOps 环境（YAML 部署作业）。不支持 Azure DevOps 的经典发布流水线。

无连接时

VS Code 扩展也可以在本地定义环境：通过一个始终指向已部署代码的分支，或者通过一个标签模式。参见 VS Code 扩展。

每个环境一张卡片：现在运行的是什么，以前运行的又是什么。

页眉显示服务、环境数量，以及最近一次部署的时间和所在环境。刷新按钮会重新加载部署。

环境卡片

每个环境都有一张卡片，显示环境名称、部署次数和最新部署的状态。对比会将此环境设为对比环境中的目标；当服务报告了环境的 URL 时，打开会打开该 URL。

顶部的四项信息描述当前线上的部署：

信息内容
版本已部署提交上的标签。点击它会在该标签处打开“历史记录”页面。没有标签时，显示已部署的引用。
提交短 SHA，带有复制按钮。
部署时间部署距今多久，以及由谁部署。
流水线流水线和运行编号，点击详细信息可在服务上打开该部署。

当最新的部署不是线上部署时（因为它失败了、被取消了或仍在运行），会有一个提示栏说明这一点，并指出该环境仍在运行哪个版本。没有成功部署的环境会显示“尚无成功的部署”。

部署历史

在这些信息下方，历史记录按从新到旧的顺序列出各次部署：日期、状态、版本、提交、部署者和变更。线上标记当前正在运行的部署。卡片显示八次部署；显示全部会列出其余部署。

用变更列中的切换按钮展开某一行，即可以变更集的形式查看该次部署与它所替换的部署相比带来了什么：

  • 成功的部署显示“带来了 N 个变更集”，失败的部署显示“本应带来”；
  • 当部署回退到较旧的版本（回滚）时，显示“移除了 N 个变更集”；
  • 第一次部署显示“首次记录的部署：没有可对比的对象”。

一次部署与它所替换的部署相比带来了什么。

对比环境

页面顶部的对比环境面板以变更集的形式回答“把预发布环境部署到生产环境会带来什么？”这个问题。

将 Staging 部署到 Production：会带来什么，以及由谁批准。

选择两侧

已上线于是将接收部署的环境。对比是你要部署的内容：另一个环境，或默认分支（“尚未部署”）。交换按钮会互换两侧；环境卡片上的对比按钮会将该环境设为已上线于。

第一次对比会自动选好：生产环境（名称包含 prod 或 live 的环境，否则为最久之前部署的环境）对比最近部署的另一个环境。只有一个环境时，会将默认分支与它对比。

阅读结果

摘要说明部署会产生什么结果：

结果含义
“将 Staging 部署到 Production 会带来 N 个变更集（M 个提交）”下方列出的变更将到达该环境。
“Production 和 Staging 运行的是同一个提交”没有需要部署的内容。
“Production 包含 Staging 所没有的 N 个变更集”部署会移除它们。
“Production 还包含 Staging 所没有的 N 个变更集（例如未合并回来的热修复）”两侧都有各自的变更；线上环境的变更单独列在仅在 … 中部分。
某个提交不在本地仓库中点击获取，随后对比会重新运行。

每个变更集显示：

  • Keep a Changelog 的类别（新增、变更、弃用、移除、修复、安全），取自标题的约定式提交前缀（feat:、fix:…）、分支前缀（feature/、fix/…）或拉取请求的标记，否则为“变更”；破坏性变更标有破坏性；
  • 标题、拉取请求链接、分支、作者、日期和提交数量；
  • 内务类变更（文档、测试、CI、杂项）标有内部，以淡色显示，并且不纳入发布说明；
  • 审阅状态：已由 … 批准、未批准、无拉取请求，或在服务未报告批准情况时显示审阅情况未知。

每一侧最多列出最新的 500 个变更集；列表被截断时，面板会给出提示。

线上环境有一项另一侧缺少的变更：部署会将其移除。

分享结果

复制发布说明会将这些变更复制为 Keep a Changelog 格式的 Markdown，仅包含面向用户的变更。导出审计报告… 会将恰好涵盖这些变更的审计报告保存为 HTML、Markdown、CSV 或 JSON。

部署的审计报告

审计报告记录你所对比的范围：每项变更由谁编写、由谁集成、是否经过拉取请求以及由谁批准、它的风险，另外还有一份需要关注的变更的摘要。保存后，通知会给出概要（“12 项变更 · 2 项无拉取请求 · 1 项高风险 · 0 项未批准”），打开会在浏览器中打开 HTML 报告，或在其所在文件夹中显示其他格式的报告。

发布审批证据

在每次生产部署之前，导出 staging → production 的报告，并将其与发布一起保存：它记录了哪些内容上线以及由谁批准。参见变更审计报告。

后续步骤

变更审计报告 → 报告包含哪些内容，以及如何验证它。 流水线 → 每次部署背后的运行。
